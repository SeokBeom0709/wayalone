# 성능·동시성 개선 기록

측정한 것만 적었습니다. 환경은 개인 PC(Windows, Docker의 MySQL 8.4와 Redis 7)이고, 데이터는 직접 만든 합성 데이터라 절대값보다 **비교 결과**를 봐 주세요.

## 1. 반경 검색 쿼리와 인덱스

우리 DB에 등록된 장소(`place`)를 "내 주변 N m"로 찾는 쿼리(`GET /api/places/around`)입니다. (주변 식당 `/nearby`는 카카오 API를 호출하므로 이 쿼리와 무관합니다.)

**조건**: 100만 행. 절반은 전국에 균등하게, 절반은 서울 수도권에 몰아서 생성. 서울 시청 부근과 인구가 적은 지역에서 반경별로 조회. 각 질의를 5~50번 반복한 평균(ms).

| 질의 (결과 건수) | A 거리 계산만 | B1 사각형 + 인덱스(위도) | **B2 사각형 + 인덱스(위도, 경도)** | C SPATIAL 인덱스 |
|---|---:|---:|---:|---:|
| 서울 300m (132건) | 604 | 52 | **1.0** | 1.4 |
| 서울 1km (1,314건) | 629 | 756 | **5.7** | 10.4 |
| 서울 3km (11,982건) | 579 | 2,212 | **106** | 1,510 |
| 비수도권 1km (8건) | 508 | 3.7 | **0.2** | 0.08 |

- A: `WHERE haversine(...) <= 반경`. 모든 행에 삼각함수를 계산합니다.
- B: 먼저 좌표 사각형(`BETWEEN`)으로 후보를 좁히고, 남은 행에만 Haversine 계산.
- C: `POINT` 컬럼에 `SPATIAL INDEX`를 만들고 `MBRContains`로 후보를 좁힌 뒤 Haversine 계산.

**실행 계획 (EXPLAIN)**

| | type | key | 예상 rows |
|---|---|---|---:|
| A | `ALL` (전체 스캔) | 없음 | 988,961 |
| B2 | `range` | `idx_lat_lng` | 63,178 (실제 읽은 행은 EXPLAIN ANALYZE 기준 1,357, 9ms) |
| C | `range` | `sp_location` | 397 |

**확인한 것**
1. 거리 계산을 `WHERE`에 바로 쓰면 인덱스를 쓸 수 없어 100만 행에서 약 0.5~0.6초가 걸리고, 반경이 달라도 비슷합니다. (전체 스캔 확인)
2. 사각형으로 좁혀도 **인덱스가 위도 하나뿐이면 오히려 느려질 수 있습니다.** 서울 1km는 629ms → 756ms, 3km는 약 4배 느렸습니다. 위도 띠에 걸리는 행이 많고, 그 행마다 본 테이블을 다시 읽기 때문입니다.
3. **(위도, 경도) 복합 인덱스**를 쓰면 서울 1km가 629ms → 5.7ms로 약 110배 빨라졌습니다. 경도 조건도 인덱스 안에서 걸러져서 본 테이블을 읽는 행이 줄어듭니다.
4. SPATIAL 인덱스는 이 데이터에서 복합 인덱스보다 빠르지 않았습니다. 후보가 많은 3km에서는 1.5초로 크게 느렸고, 후보가 거의 없는 지역에서만 더 빨랐습니다.

**적용한 방식**: B2. SPATIAL이 이 규모에서 이점이 없고, 컬럼 타입 변경이 필요하며, 개발·테스트용 H2에서 쓸 수 없기 때문입니다. 코드는 `PlaceRepository.findWithinRadius`, 인덱스는 `Place`의 `idx_place_lat_lng`입니다. 사각형은 서버에서 위도 1도 ≈ 111.32km, 경도는 위도에 따라 보정해서 계산하고, 정확한 거리는 Haversine으로 한 번 더 걸러 가까운 순으로 자릅니다.

**한계**
- 합성 데이터입니다. 실제 분포(밀집 지역, 업종 편중)에서는 수치가 달라질 수 있습니다.
- 같은 PC에서도 실행마다 수십 % 흔들립니다. (예: A는 400~630ms를 오갔습니다.)
- 서비스의 장소 데이터는 지금 10건이라 이 인덱스의 효과는 데이터가 늘어난 뒤의 이야기입니다.

재현: `docs/benchmarks/geo/run.ps1` (별도 DB `geo_bench`에서만 실행하고 끝나면 삭제). 원본 출력은 `docs/benchmarks/geo/result-2026-10-21.txt`.

## 2. 장소 목록의 N+1 쿼리

장소 10개를 조회할 때 실행된 SQL 개수를 Hibernate 통계로 측정했습니다. (`PlaceQueryCountTests`)

| | 실행된 SQL |
|---|---:|
| 개선 전 | **31개** (= 1 + 장소마다 3개) |
| 개선 후 | **3개** |

- 원인: 장소마다 (1) 태그(`@ElementCollection` EAGER)를 따로 읽고, (2) 평균 별점과 (3) 후기 수를 각각 쿼리로 조회했습니다.
- 수정: 태그는 `@BatchSize(100)`으로 한 번에, 별점과 후기 수는 `GROUP BY` 쿼리 하나로 목록 전체를 조회.
- 장소가 늘어도 SQL 개수가 늘지 않는지를 테스트로 고정했습니다.

## 3. 인증번호·1회용 토큰의 동시성과 Redis

### 문제 (재현됨)
인증 요청을 같은 번호로 24개 동시에 보내는 테스트를 만들어 기존 DB 구현에 돌렸습니다. (한 번 실행 기준이며 실행마다 숫자는 달라집니다.)

| 시나리오 | 기대 | 실제 |
|---|---|---|
| 같은 1회용 토큰으로 동시에 가입 | 성공 1번 | **10번** |
| 맞는 인증번호로 동시에 확인 | 토큰 1개 발급 | **10개** |
| 틀린 인증번호를 동시에 24번 | 5번까지만 인정 | **24번 모두 인정** (시도 제한이 무력화됨) |

원인은 "읽고, 판단하고, 쓰기"가 한 트랜잭션 안에서 나뉘어 있어서 동시 요청이 같은 상태를 읽는 것이었습니다. 6자리 인증번호를 병렬 요청으로 대입할 수 있다는 뜻이므로 보안 문제이기도 합니다.

### 수정
`VerificationStore` 인터페이스로 저장소를 분리하고 두 구현을 만들었습니다. (`app.verification.store=db|redis`, 기본값 db)

| | DB (기본) | Redis |
|---|---|---|
| 유효시간 | 만료 시각 컬럼 + 오래된 행 삭제 | 키 TTL (인증번호 3분, 토큰 30분, 재발송 간격 60초, 하루 한도 24시간) |
| 틀린 횟수 | 조건부 `UPDATE attempts = attempts + 1 WHERE attempts < 5` | 인증번호와 확인을 Lua 스크립트 한 번으로 처리 |
| 인증 성공 | `UPDATE ... WHERE verifiedAt IS NULL` 영향 행 1개일 때만 성공 | 같은 스크립트 안에서 인증번호 삭제와 토큰 저장 |
| 토큰 1회 사용 | `UPDATE ... WHERE usedAt IS NULL` | 읽기+삭제를 스크립트 한 번으로 |
| 발송 한도·재발송 간격 | 확인 후 저장 (이 부분은 동시 요청 보호를 하지 않았고 테스트도 없음) | 스크립트 한 번으로 원자적 처리 |
| IP별 시간당 한도 | 서버 메모리 (서버 1대 기준) | Redis (여러 서버가 공유) |
| 가입 실패(롤백) 시 | 트랜잭션 롤백이 사용 처리를 되돌림 | 트랜잭션이 끝난 뒤 롤백이면 토큰을 직접 복구 |

Redis 키에는 전화번호 원문이 아니라 HMAC 해시만 들어갑니다.

### 결과
- 위 3개 시나리오가 두 구현 모두에서 통과합니다. (기대값대로 토큰은 1번만 소비, 시도는 5번까지만 인정)
- Redis 전용 테스트: 키에 TTL이 걸리는지, TTL이 지나면 만료되는지, 같은 번호로 동시에 발송하면 1건만 발송되는지, 새 인증번호를 받으면 틀린 횟수가 초기화되는지.
- 실제 MySQL + Redis를 띄운 서버에서 발송, 오입력, 확인, 가입, 같은 토큰으로 재가입 시도까지 확인했습니다.

### 트레이드오프
- Redis가 죽으면 인증이 안 됩니다. (인증을 건너뛰지 않고 실패시킵니다.)
- 인증번호는 몇 분 뒤 사라지는 값이라 Redis를 영속 저장 없이 씁니다. 재시작하면 진행 중이던 인증이 사라집니다.
- 서버를 한 대만 쓸 때는 DB 구현으로 충분합니다. Redis는 서버를 늘리거나 TTL로 관리하고 싶을 때 켭니다.
- 처리량(초당 요청 수)은 측정하지 않았습니다. 이 작업의 목적은 속도가 아니라 동시 요청에서 규칙이 지켜지는 것입니다.
